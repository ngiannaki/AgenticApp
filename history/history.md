## 2026-09-22
- **Change:** Added deterministic answer citations to the chat, plus a Documents-page raw chunk browser (with tags) for inspection/preview
- **Files:** backend/mcp_servers/retrieval/langchain_pipeline.py, backend/mcp_servers/retrieval/server.py, backend/apps/api/streaming_agent.py, backend/apps/api/events.py, backend/apps/api/routers/chat.py, backend/apps/api/routers/files.py, backend/apps/client/config.py, frontend/src/lib/types.ts, frontend/src/lib/api.ts, frontend/src/components/ChatApp.tsx, frontend/src/components/ChatWindow.tsx, frontend/src/app/documents/page.tsx, frontend/src/app/globals.css
- **Details:** Two features, one shared new MCP tool:
  1. **Citations**: every `retrieve_document_v2` tool result's `grounding` blocks (already carrying document_id/chunk_id/page/section) are collected server-side across a whole chat turn, deduped by `chunk_id` in first-appearance order, and sent as a new `citations` SSE event (`events.citations`, persisted as a `citations`-type step in `routers/chat.py`) right before the final `message` event — deliberately not self-reported by the model, so the citation list can't be hallucinated. `DEFAULT_SYSTEM_PROMPT` (backend/apps/client/config.py) now asks the model to drop matching `[1]`/`[2]` markers in its prose, numbered in that same first-appearance order. It's registered as an MCP tool (so the FastAPI process can reach it via `runtime.mcp.call_tool`, same as other indexing/retrieval tools) but deliberately excluded from the chat agent's own tool list (`_INTERNAL_ONLY_TOOLS` in streaming_agent.py) since the model has no use for an unscored raw dump. Exposed via a new REST endpoint `GET /api/documents/{id}/chunks` (routers/files.py, ownership-checked like the existing content endpoint), consumed by a new "Preview chunks" action (layers icon) on the Documents page that expands an inline panel listing every chunk with its tags (chunk_id, chunk_index, page/sheet/row, chunk_content_type, section) and text.

## 2026-09-24
- **Change:** Fixed a silent scanned-PDF indexing gap, and added legacy `.xls`/`.ods` spreadsheet support to v2 indexing
- **Files:** backend/mcp_servers/indexing/langchain_structure.py, backend/mcp_servers/indexing/langchain_loaders.py, backend/mcp_servers/indexing/parsers/detect.py, backend/mcp_servers/indexing/parsers/xlsx_reader.py, backend/mcp_servers/indexing/requirements.txt
- **Details:** Prompted by reviewing Anthropic's `file-reading` skill (backend/skills/SKILL.md, a claude.ai-uploads router, not directly usable in this headless backend) for portable ideas — two gaps stood out and were fixed:
  1. **Scanned-PDF OCR fallback**: `pdf_to_documents` (langchain_structure.py) previously always used the configured engine (docling, `use_ocr=False` hardcoded, or pymupdf4llm — neither does OCR), so a scanned/rasterized PDF with no text layer silently parsed to near-empty pages, got filtered out by the blank-content check in `load_documents_v2`, and indexed with little/no content and no error or warning. Added `_pdf_has_text_layer` (samples the first 3 pages via `pymupdf`'s `page.get_text()`, mirroring the skill's `pdffonts` diagnostic) run up front; when it returns `False`, the PDF is routed to a second, OCR-enabled Docling `HierarchicalParser` singleton (`_get_docling_parser(use_ocr=True)` — kept separate from the non-OCR singleton since Docling bakes `do_ocr` into the pipeline at construction time) instead of the configured engine, only falling back to plain-text extraction if OCR itself is unavailable or fails.
  2. **Legacy spreadsheet support**: `.xls` and `.ods` weren't in `detect.py`'s extension map at all (would error as an unrecognized extension) and even if content-typed correctly, `parsers/xlsx_reader.py::parse_xlsx` only supported openpyxl (which raises `InvalidFileException` on both formats). Mapped `.xls`/`.ods` to the existing `"xlsx"` content type in `detect.py`, added a `_parse_legacy` path in `xlsx_reader.py` that routes through `pandas.read_excel` with `engine="xlrd"` (`.xls`) or `engine="odf"` (`.ods`), and made v2's `_load_xlsx` skip `UnstructuredExcelLoader` (xlsx/xlsm-only) for these two extensions so they go straight to the now-working fallback. `xlrd`/`odfpy` installed into the project venv and added to requirements.txt as soft dependencies (pandas was already present transitively); round-tripped against a generated `.ods` file to confirm sheet/header/row extraction works.

Written deliberately as concrete imperative checklists rather than prose, because the chat model is `gpt-oss:20b` (DEV) / `gpt-4o-mini` (PROD), not a frontier model, and subtle guidance doesn't survive that. Every limit quoted in them is read from real config rather than invented (query caps from `DbMcpSettings`, sandbox timeout/output/artifact caps from `CodeMcpSettings`, `max_top_k`/`max_tool_result_chars` from `LangchainRagSettings`/`ApiSettings`).

Added `_cited_only(citations, answer)` in streaming_agent.py: parses `[n]` markers out of the final answer and keeps only those citations, applied on both the normal and forced-final-answer paths. - **Change:** Root-caused and fixed the subprocess-duplication bug flagged as unresolved in the 2026-09-30 todo entries ("Root-cause the actual subprocess-duplication bug properly") — every new chat session (and every files.py upload/delete call) was re-running the MCP `initialize` handshake against all 4 servers under Docker/stdio transport, causing the ~10-25s "Starting MCP server..." delay the user reported seeing on every "+ New chat" click, and occasionally breaking other concurrent sessions' in-flight requests

- **Details:** Traced the actual bug by reading the installed `fastmcp`/`mcp` library source rather than trusting `new_client()`'s docstring (which claimed `keep_alive=True` made this cheap under stdio). Found it's transport-dependent, and the 2026-09-30 fix only ever worked correctly for one of the two transports this app supports:
  - **HTTP (`servers.json`, `start_mcp_servers.ps1`)**: `StreamableHttpTransport.connect_session` (`fastmcp/client/transports/http.py:150-204`) opens a genuinely new `ClientSession`/HTTP connection per `Client.new()` + `__aenter__()`. This was always correct and is unchanged by today's fix — every chat session already gets a real, independently isolated MCP connection here.
  - **stdio (`servers.docker.json`, the Docker image)**: `StdioTransport.connect()` (`fastmcp/client/transports/stdio.py:83-94`) is a documented no-op once already connected — it returns the exact same underlying `ClientSession`, not a new one. But `Client.new()` resets the new `Client` wrapper's cached `initialize_result` to `None`, so its `__aenter__()` still calls `self.session.initialize()` — sending a second `InitializeRequest` down the *same shared pipe* to all 4 subprocesses. The MCP server side (`mcp/server/session.py:171-205`) accepts a second initialize unconditionally, but briefly flips its state back to `Initializing` while handling it, during which **any other in-flight request on that same shared session gets rejected** with `"Received request before initialization was complete"`. This explains both halves of the reported symptom: the visible delay (4 servers re-handshaking on every new chat) and "it does not create one" (a concurrently in-flight request from another tab/session getting killed by the race).
  - **Fix**: `AgentRuntime` now detects which transport mode is active once, at `connect()` time (`isolated_sessions = not any("command" in cfg for cfg in servers["mcpServers"].values())`), and exposes a single `acquire_session_client()` method returning `(client, owns_lifecycle)`. Over HTTP it behaves exactly as before (fresh, owned, isolated client). Over stdio it now hands back the one already-initialized shared `self.mcp` client directly and reports `owns_lifecycle=False` — no new connection, no duplicate initialize, zero added latency. `SessionManager.create`/`restore` (sessions.py) store `mcp_owns_lifecycle` on `ChatSession` and `SessionManager.delete`/`evict_idle` now only `__aexit__` the client when the session actually owns it — critical, since blindly closing the shared stdio client on the first idle-session eviction would have torn down MCP connectivity for the entire app. `call_tool_isolated` (used by files.py's upload/delete endpoints, which had the identical latent bug) was fixed the same way.
  - **Why this is safe for concurrent multi-user/multi-conversation use** (the stated goal — a "professional app" supporting many users and many conversations, now practical since conversations persist to Mongo and idle sessions evict/rehydrate transparently via `session_helpers.get_or_rehydrate_session`): `mcp.shared.session.BaseSession.send_request` (`mcp/shared/session.py:240-314`) gives every request its own ID and its own dedicated response stream, with `finally`-block cleanup scoped only to that one request — concurrent calls on one shared session are standard JSON-RPC multiplexing and don't interfere with each other, and cancelling/timing out one request never touches another's state. `routers/data.py` already relied on exactly this (calling `runtime.mcp.call_tool` directly, concurrently with whatever sessions are doing) before today's fix, so this isn't a new assumption — the fix just applies the same, already-proven-safe pattern to session creation instead of special-casing one router around the bug.

Now async, and actually probes `runtime.mcp.ping()` (which itself goes through the same reconnect logic) and `conversation_store.client.admin.command("ping")` for Mongo, each under a 5s timeout, returning `{"status": "degraded", "checks": {...}}` with a 503 status code if either is unreachable.
  - **Scope note**: resilience is deliberately scoped to the shared stdio client only — `ResilientMcpClient.new()` (used by `acquire_session_client` under HTTP transport) delegates straight through to the underlying raw client's `.new()`, unwrapped, same as before this change. Isolated HTTP sessions weren't implicated in today's incident and already get a fresh client per session via `SessionManager`.
